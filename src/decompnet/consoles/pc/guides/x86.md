# x86 and MSVC (PC, original Xbox)

Registers: eax return value; eax, ecx, edx scratch; ebx, esi, edi, ebp callee-saved; esp stack.

Calling conventions (read them off the call sites)
- __cdecl: arguments pushed right to left, caller cleans up (`add esp, N` after the call).
- __stdcall: callee cleans up (`ret N`). Win32 API calls.
- __thiscall: MSVC member functions; `this` in ecx, callee cleans up.
- __fastcall: first two arguments in ecx, edx.

Frames: `push ebp; mov ebp, esp; sub esp, N` with locals at [ebp-x] and arguments from [ebp+8]; with
frame-pointer omission (/Oy) everything is esp-relative and offsets shift with each push.

Matching MSVC (versions 4.x-7.1 for older games, 2005-2010 for newer ones; the project fixes version and flags)
- /O2 vs /O1 changes idioms (`xor eax, eax`, `rep movsd`, intrinsic `memcpy`/`strlen`).
- Local declaration order and types change stack offsets and register choice.
- `switch` with dense cases becomes `jmp [table + eax*4]`; MSVC also builds byte index tables.
- x87 floating point: `fld`/`fstp`, compares via `fcomp` + `fnstsw ax` + `test ah, 41h`; float to int
  calls `__ftol` (older MSVC) unless the project uses other flags.
- SEH frames (`push -1; push handler; mov eax, fs:[0]`) and `mov [ebp-4], N` state updates come from
  C++ objects with destructors in scope or try/catch.
- Virtual calls: `mov eax, [ecx]; call [eax + off]`.
- From 2005 on, /GS is on by default: a function with a local array or buffer starts with
  `mov eax, [___security_cookie]; xor eax, esp` (or ebp), stores it below the locals and ends with
  `call @__security_check_cookie@4`. The compiler makes all of it: write the array, never the cookie.
- A function that builds an ebp frame it doesn't need (`push ebp; mov ebp, esp; pop ebp; jmp f` forwarding its
  arguments) was compiled with frame pointers (/Oy-), which the project's /O2 leaves out: put
  `#pragma optimize("y", off)` on the line above the function and `#pragma optimize("", on)` on the line below.
  In a PC game started from scratch, a source file whose functions mostly keep a frame is built with /Oy-
  already (config/<version>/file_flags.json); search_flags(function) tries the file with and without it (and /O1,
  /Ob1) and keeps what matches.

A game's own DLLs are programs of the project too: a DLL's source files are in `src/auto/<its name>/` (a new file
of it goes there too), its functions are named by the address the project gives it, and the ones it exports by
the name it exports them by (write that name). A call into another DLL or the .exe goes through the import table,
`call [__imp__Name]`, like any import (below): never call another program's function by its address.

Annotation-based projects (reccmp) mark functions with comments such as `// FUNCTION: GAME 0x401000`
above each definition; keep them exactly as the project writes them.

PC games started from scratch in decompdecomp (Ghidra + objdiff)
- Source files are C++ (src/auto/text_<address>.cpp), built with exceptions on (/GX; /EHsc from 2005 on), as games
  of the time were: classes, constructors and destructors, try/catch, new/delete and the STL all work, and so does
  plain C.
- A function is func_<address>: write it as a free function or as a class's method (`void Town::func_0041B470(int
  id)`); the build gives what it compiles to the original's symbol name, so any name mangling pairs with the game.
  Declare the class in a header (edit_file). What still has to match is the calling convention, which the code
  shows: a method gets `this` in ecx and pops its stack arguments (`ret N`); a free function is __cdecl (the caller
  cleans up), __stdcall (`ret N`) or __fastcall (arguments in ecx, edx). The symbol's decoration says which the
  original is: _f is __cdecl, _f@8 __stdcall, @f@8 __fastcall or a method.
- A program built with run-time type information (RTTI) names its classes: `get_class()` lists them (MFC's and
  the C++ library's too), and `get_class(func_0041B470)` shows a virtual function's class. Virtual functions are
  methods (`this` in ecx) whatever the symbol's decoration says. Give the class that name in your header. Without
  RTTI, classes are found from the vtables their constructors store (`Class_<vtable address>`); either way
  get_class shows their fields, and `guess_struct(function, "this")` (or "arg0" for the first stack argument)
  the likely struct behind a pointer.
- Constructors and destructors: declare the class with its own name (get_class's, when the program names it:
  `struct CFoo { CFoo(); ~CFoo(); int x; };`, edit_file into a header), then send `CFoo::CFoo() { ... }` as the
  function at one address and `CFoo::~CFoo() { ... }` as the one at another: one of them per compile_and_diff, defined outside the class. Your
  definition names the function (its real name is CFoo::CFoo from then on), and the build pairs what MSVC makes of
  it (`??0CFoo@@QAE@XZ`, `??1CFoo@@QAE@XZ`) with the original's symbol, and so every call to it from other
  functions (`new CFoo`, `CFoo x;`, `this->~CFoo()`). A name another function has is refused: an address was wrong.
  A class has one constructor name, so of two constructors at two addresses (a copy constructor) write one as a
  constructor and the other as a method. A constructor returns `this` (`mov eax, esi` before `ret`); a destructor
  doesn't. A deleting destructor (`test byte ptr [esp+8], 1`, then a call that frees `this`) is a method you write:
  `void* CFoo::func_004A8360(unsigned int flags) { this->~CFoo(); if (flags & 1) func_00631D5C(this); return
  this; }`. Where it stores a vtable (`mov dword ptr [esi], offset ...`), write that store (`void* vtbl;` first in
  the class, `vtbl = &D_0064AF70;`) instead of declaring virtual functions. A class named after the function's
  address works too (`func_004D9DD0::~func_004D9DD0()`), for one of the two.
- An exception frame (`push -1; push handler; mov eax, fs:[0]`, `mov [ebp-4], N`) means objects with destructors
  in scope or try/catch: write them in C++, the compiler makes the frame.
- Data is `D_<address>` (`extern int D_00402034;`): the original's code holds the address, so any name your C++ uses
  for it matches. read_data(D_00402034) shows its bytes. Imports are `__imp__<name>`. A `call _Sleep@4`
  (or `call _Sleep`) goes to an import thunk (set aside,
  named after its import): declare the function without dllimport (`extern "C" void __stdcall Sleep(DWORD);`).
- A switch's jump table sits right after the function's code, as MSVC puts it; it matches on its own.
- A game that shipped its debug information (a .pdb, the linker's .map, or COFF symbols in the .exe) was imported
  with it: its source files are the game's own (src/auto/<name>.cpp for its <name>.cpp), its functions and data
  have their real names (functions.json's "names": write `entity_spawn`, `g_player`, or a method as
  `Town::Update`, and the build pairs it with the game's symbol), and a program database also gives every type and
  global in include/debug_types.h (common.h includes it) and each function's prototype, parameters and locals in its
  brief. Use those names and types as they are: the offsets are the game's, and the free functions are declared
  there already.
- Library code (the C runtime, DirectX helpers) is in the program too: hand-written assembly such as `_ftol` can't
  be written in C++; release it with a note.
