# SN Systems N64 GCC

SN64 GCC 2.8.1 and 2.7.2 builds 0001, 0004 and 0006 are distinct
compiler/assembler profiles.
They are alternatives to KMC, not interchangeable GCC version labels.

The app preprocesses with that release's cppn64, runs its original cc1n64 and
asn64 through wibo, then converts the PsyQ object to big-endian ELF using a
pinned PCSX-Redux converter. The ordinary linker and byte comparison decide
the match. A familiar-looking disassembly or a low score is not proof.

Builds 0001 and 0006 also include their own C++ frontends. The app tries C first, then C++ for code that needs it; build 0001 paired with the 0004 assembler has the same C++ frontend as 0001. The preserved 0004 pack does not include its C++ frontend. These are comparison options, not evidence of a game’s original compiler.

Use try_compiler on existing C before proposing a compiler range. Try several
nontrivial functions in that part of the game, including calls, data accesses
and floating point. Library code may use a different compiler from game code.
Do not replace a whole game's compiler because one small function matches.

SN64 2.8.1 defaults to -O2 -G0 -mips3 -mgas -meb -mcpu=VR4300 -mhard-float -mfp64.
Build 0001 does not accept -mcpu=VR4300; its default profile omits that option
and -mfp64. search_flags can test optimisation and small-data settings.

SN64 2.8.1 needs ASN64 2.78: an older assembler rejects its %hi/%lo operands.
If an older installation contains only cc1n64.exe, reinstall it in Compilers
& tools to obtain its pinned preprocessor and assembler too. Installation
still requires explicit acceptance of proprietary tools.

The converter needs a C++20 host compiler and zlib headers at first install
(Xcode Command Line Tools on macOS; g++ and zlib1g-dev on Linux/WSL). It is
built once; matching does not rebuild it for every function.

The reconstructed `sn-n64-272-970404` profile is separate from those original
packs. It runs native cpp/cc1, the pinned modern-asn64 compatibility wrapper,
and GNU binutils, producing ELF directly. Its default `-fno-exceptions`
avoids the reconstruction's exception-enabled default for C. On macOS the
installer builds the pinned source with Xcode Command Line Tools; Linux uses
a pinned prebuilt release. It is not proof of equivalence to an original SN build.
Its passes (`sched.c`, `reorg.c`, `config/mips/`) are installed beside it as `sn64-gcc-2.7.2-source`
(`toolchains.source_for`); the original packs have no source.

Builds 0004 and 0006 retain their own assemblers. Build 0004 uses the pinned
2.8.1 preprocessor, as does 0001. Installation of original packs still requires
license acceptance. All profiles use the ordinary linker and byte judge.

## Reading the compiler's passes

The SN profiles' cc1 writes the usual GCC pass dumps with `-da`, and decompdecomp runs it for you: the
`compiler_passes` tool gives the allocation table, preferences, scheduler orders and the loop optimizer's notes (which
insns it hoisted and "moved to", the bivs and givs it found, what it combined or refused) for any SN profile, as for the
KMC GCC ones. To read the raw dumps, run the compiler proper on the preprocessed C yourself (`cc1n64.exe -quiet <flags> -da
FILE.i -o FILE.s` under wibo; the dumps are `FILE.i.lreg`, `.greg`, `.loop`, `.sched`, `.sched2`, ...).
